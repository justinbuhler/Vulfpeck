# 0018. The task loop turns labelled issues into merged pull requests

Status: proposed
Date: 2026-10-23
Components: scripts/task_loop.py

## Context

`land.sh` stops at local `main` and nothing reads GitHub issues or publishes (HARNESS.md open gap 5), so every task needs a human to pick it, brief a worker, push and merge. An unattended loop that merges is the highest-consequence component of the harness: it must pick work only from a source the owner controls, never lower a test tier, stop on repeated failure, and merge only on green CI. Codex 0.164 loads project hooks only from the main checkout's `.codex/hooks.json`, so a Codex worker in a worktree can run with no gates.

## Decision

`scripts/task_loop.py` (High tier) runs intake, state, dispatch, verify, land, publish, reset and next. Its queue is the open GitHub issues carrying the `[loop] label` of `harness.toml`; the harness's own recommendations enter only as issues filed with that label (`file-followup`). Each issue has a state file under `<git common dir>/harness/tasks/` that moves only `queued -> running -> verified -> landed -> published`, or to `blocked` or `failed`; any other move raises, and only the owner's `reset` goes back.

The next issue is the highest `[loop] priority` label (none ranks last); a tie goes to a Jev choice over titles and labels at probability 0.6 or more, else the lowest issue number. A worker is the `[loop.workers]` command of the runtime, started in a worktree from `agent_harness.py provision` with a brief stating scope, forbidden actions, done-when and the report line `STATUS: DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED`. `NEEDS_CONTEXT` and `BLOCKED` end as `blocked` and are not picked again. No `--dangerously-*` flag is ever passed: `sh()` raises on one and `harness_config` rejects one in a worker command. A Codex task whose main checkout has no fresh `.codex/hooks.json` ends `blocked` (`harness_doctor.codex_main_hooks`).

The loop merges unattended only when every changed path matches a hard-coded allowlist in `task_loop.py`: `docs/**` and the root `README.md`, except any `AGENTS.md` or `CLAUDE.md` and `docs/agents/**`. A `*.md` elsewhere is not documentation: skill and agent definitions (`.agents/skills/*/SKILL.md`, `.claude/agents/*.md`) and instruction files are loaded by the runtimes. Every other path, a rename or delete included, pushes the branch, opens the pull request, comments why and ends `blocked` with reason `needs-review`; it is never merged and its verification and checks wait for the owner. The allowlist is not read from any `harness.toml` or from the worktree (Rule 11), and tiers play no part. Immediately after the fetch the runner resolves `origin/<base>` to a commit and uses only that commit afterwards (provision `--baseline`, `git show <sha>:harness.toml` for `commands.lint`, the changed-path diff, the ignore rules), because the worker can repoint the remote-tracking ref. For an allowlisted change the base's `commands.lint` runs in the worktree and must pass. Before the push the runner checks that the landed commit has exactly one parent, the pinned base commit, and judges the allowlist and the ignore rules on `git diff --name-only <base sha> <landed sha>`, because the worker can write the worktree, the manifest and the ledger; a mismatch ends `failed` with nothing pushed. The worker commits nothing: the runner refuses any changed path that the base commit's ignore files ignore (read from that commit into a scratch repository made per call with `mkdtemp` and removed afterwards, so neither the main checkout's copies nor the worktree's count) or that the provisioner reported as cloned in from the main checkout (held in memory from provision, not re-read from disk), queues the rest, and the harness lander commits them on the task branch; the loop decides the land from its own request's ledger row, not the lander's exit code. `land.sh` is not used, because it moves local `main` and `origin/main` moves only by merging a pull request (ORCH-12). The runner pushes the branch, opens the pull request (`Closes #N`, no attribution), checks that the pull request head is the landed commit, runs `gh pr checks --watch --fail-fast`, then reads `gh pr checks --json name,bucket`, and runs `gh pr merge --merge --delete-branch --match-head-commit <landed sha>` only when that list is non-empty, every bucket is `pass` and the watch exited 0. There is no `--auto`. Any other result ends `failed`, comments why and leaves the pull request open.

The issue text is untrusted: the brief fences it between markers that carry a hash of the text, puts the scope, forbidden actions and done-when after it, and refuses (`blocked`) an issue whose body was edited after its `ready-for-agent` label event. Every subprocess that runs worker-controlled code (the worker, verification, and the lander with the hooks the worker may have written) runs without `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN` and `SSH_AUTH_SOCK`, with `GH_CONFIG_DIR` set to an empty directory and `GIT_CONFIG_NOSYSTEM=1`; the branch is pushed with `core.hooksPath=/dev/null`. One runner holds an exclusive lock per issue for a whole task; a second skips it. Each attempt has its own task name (`issue-N-aK`), so a reset task provisions cleanly, and any exception, `SystemExit` included but `KeyboardInterrupt` not, ends the task `failed` so the loop still resets and counts it.

Between tasks `loop_reset.py` runs as code and is recorded. `run` stops after 2 consecutive tasks end failed or blocked, or when one issue has failed twice. `--dry-run` prints the commands of every mutating subcommand and runs none; every external call goes through `sh()`.

## Consequences

Issues labelled `ready-for-agent` can reach `main` without a person in the loop only when the change is documentation on the allowlist and the pull request's checks all pass; the rest waits for the owner. This does not change repository settings: auto-merge stays off and `main` stays unprotected, so a green check is the only gate below High; branch protection (open gap 1) is the stronger control. **This does not contain a hostile worker that runs as the owner:** it still reaches the keyring, ssh keys on disk and everything else the owner can read, which dropping environment variables does not remove. Only a sandbox plus branch protection contains it, and enabling the loop on a real repository requires both. Known gaps: the loop does not wait for checks to register or compare required check names, and the stale-text check covers body edits only, not a title rename or who applied the label. The reset clears the `task-loop` session only: the worker's own session id is not known to the runner, so a worker's loop and budget counters are not cleared. A Codex task needs main's hooks synced first; a standalone `git clone --shared` worker is not built. The merged task's worktree and local branch are left for the owner to remove. A repository with no checks reports `gh pr checks` failure and every task ends `failed`. The loop is not run against the real repository by this change.
